# Verify Task 16: Backend Architecture & API Integration Logic

## Какво трябва да се провери ръчно
1. **API Изолация**: Отворете Network tab в браузъра и проверете заявките по време на генериране на отчет. Не трябва да има директни заявки към `google.com` или `facebook.com`. Всички заявки трябва да са към вътрешни пътища (напр. `/api/...`).
2. **Сигурност на тоукъните**: Уверете се, че никъде във фронтенд стейта или в API отговорите не се съдържат OAuth `access_tokens`.
3. **Token Refresh**: Симулирайте изтекъл тоукън и проверете дали бекендът автоматично го опреснява и връща данните успешно без намеса на потребителя.
4. **Консистентност на данните**: Проверете дали изчисленият CTR в превюто съвпада с ръчно изчисление от суровите данни (Clicks/Impressions) – логиката трябва да е на бекенда.
5. **Изолация на потребители**: Опитайте се да извикате вътрешно API с ID на проект, който не принадлежи на текущия потребител – бекендът трябва да върне 403 Forbidden или 404 Not Found.

## Какво трябва да се види на екрана
- Превю режимът се зарежда коректно с данни, доставени от вътрешните API ендпойнти.
- Липса на технически грешки, свързани с аутентикация в конзолата на браузъра.

## Какво поведение се очаква
- Бекендът действа като "черна кутия", която приема прости заявки и връща готови за показване данни.
- Пълна прозрачност за потребителя при процеси като опресняване на тоукъни.

## Какво не трябва да е счупено
- Генерирането на PDF (той трябва да ползва същата бекенд логика за данни).
- Свързването на нови акаунти (OAuth flow).

## Критерии за успешно изпълнение
- Бекендът осигурява защитена, стабилна и скалируема основа за всички маркетингови данни в приложението.

## Оставащи рискове или непотвърдени точки
- Поведение при промяна на API версиите от страна на Google/Meta (нужда от регулярна поддръжка).
